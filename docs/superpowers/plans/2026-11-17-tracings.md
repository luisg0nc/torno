# Tracings: implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A **tracing** `T<n>` is the model laid flat in one plane at true scale, on a millimetre grid. Its outline is
the kernel's exact cut, redrawn after every build, on a face, a main plane or the section on screen. A photo lies
under it, lined up by 2 or 4 points. The person and Claude add named, coloured layers in the tracing's mm. The person
reviews on it with pins, ink, `span` measures and `offset` marks ("should be here"). It is a third view
(Board | Model | Tracing), a card on the board, a picture for Claude, and a true-scale SVG or PDF export. One PR, three
phases, every suite green at the end of each.

**Architecture:**
- One file, `<object>/.torno/tracings.json` (`{ next, tracings }`), travels in git. `TracingStore`
  (`main/tracings/store.ts`, made as `board/store.ts` is) is its one writer. The pure types and rules live in
  `shared/tracings.ts`, and the line-up maths in `shared/lineup.ts`. Photos, their straightened copies, `dropped.json`
  and `told.json` live in `<object>/.torno/tracings/`, which does not travel.
- The outline is never stored. `main/tracings/outline.ts` asks the kernel's `section` with the tracing's own axes and
  `snaps: true`, keeps the last two cuts per tracing in memory, and cuts again the tracings that are shown after each
  successful build (`builds.on('scene')` in `main/ipc.ts`, beside `reanchor` and `alignChecks`). A face tracing's
  plane follows its face along its normal there too.
- One pure drawing, `tracingSvg(cut, info, extras)`, in `shared/tracingSvg.ts`. The window and main both need it, and
  the renderer never imports `main/`, so it sits in `shared/` (the spec names `main/export/tracingSvg.ts`; this is the
  one move). `main/export/sectionSvg.ts` keeps `sectionSvg(cut, info)` as a call to it with no extras. The view, the
  board card, Claude's picture and the export all draw from it.
- In the window: `state/tracings.ts` (Zustand) holds the tracings of the open project and their outlines.
  `ui/tracings/` holds the view (`TracingView.tsx`), the panel, the palette, the line-up view, and the tools as pure
  pointer handlers. The view is SVG in a layer moved by a transform set on the element. `viewport/tracings.ts` draws
  Show in 3D.
- Marks on a tracing are ordinary marks in `marks.json` with `tracing: 'T1'` (`MarkStore` stays their one writer). Two
  new kinds, `span` and `offset`, carry no review intent.
- Claude: three tools in `main/mcp/tracingTools.ts` (`tracings`, `add_tracing`, `add_layer`), one shared line of
  `SERVER_INSTRUCTIONS`, a `tracings:` line in every prompt (`contextFor`), and one sentence in the agent prompt.

**Tech stack:** Electron, TypeScript, React, three.js, SVG, vitest, Playwright (hidden window), Python (build123d/OCP,
pytest).

**Spec:** `docs/superpowers/specs/2026-11-17-tracings-design.md`. Read it whole, "Builder's questions, settled" most of
all: where it differs from the Design section, the settled answer wins. The mockups are Drawing-A (the view), Drawing-B
(lining up) and Drawing-C (the tools and the drag), row 7 of the design canvas.

**Base:** `work/tracings` stacks on `work/sets`, which stacks on `main` (which already has 3D sketches #200 and reviews
#201). Sets also touch `SERVER_INSTRUCTIONS` (its `add_set` line), `REF` in `shared/chat.ts`, `prompt.ts` and the
Layers panel. Rebase on `work/sets` before Tasks 7, 8 and 13, and fit within what sets left.

**Names:** the view note's ink is `drawing` in code (`shared/drawing.ts`, `sessions/drawing.ts`, `ui/drawing/`), and
nothing is called `tracing` today. Everything new is `tracings` (plural) or `Tracing*`.

## Global Constraints

- **`T<n>` ids are main's, given from `next`, and never reused**: not after a removal, not after an undo, and not after
  a pull that brings a lower `next` (the reader raises `next` above every `T<n>` it holds). The same holds for layer
  ids within a tracing.
- **One writer.** Main is the only writer of `tracings.json`: one change at a time per project, written atomically
  (`writeOwn`, `writeFileAtomic`) before it is told. The window (`tracings:*`) and the tools (`add_tracing`,
  `add_layer`) both go through `TracingStore`. Before every write main compares the file with the text it last read or
  wrote, and builds on the disk's version when they differ (a git pull), as the board does. `id`, `by`, a layer's `id`
  and `by`, `transform`, `scale`, `angle`, `fit`, `file`, `sha256` and `straightened` are main's
  (`TRACING_MAIN_ONLY`), never taken from the window or a tool. Marks on a tracing live in `marks.json`, written by
  `MarkStore`. There is no second store of marks.
- **Photos stay local.** They live in `.torno/tracings/photos/`, with a `.gitignore` of `*` written by whoever makes
  the folder. They are **swept only through `.torno/tracings/photos/dropped.json`** (`main/dropped.ts`), once per project
  per run. A listed file goes only when no tracing names it, nothing removed in this run names it, it is a plain file
  and it is older than a minute. An unlisted file is never deleted. `.torno/tracings/told.json` goes through
  `ensureIgnored`.
- **Nothing from a photo is ever exact**: not its scale, angle or fit, not a point clicked on it, not an offset, not a
  measure with an end on it. Every number told to Claude is the kernel's and says whether it is exact
  (`exactness-app`). The outline's points are within the deflection the kernel says.
- **A `span` is exact only with both ends snapped** to kernel points of the build it was placed on (a corner of the
  cut, a hole centre, a vertex in the plane). Main works the value out from those kernel numbers and says
  `exact on build N`. Any other span is `≈`, says how (`on the photo, lined up with fit 0.4 mm` or `freehand`), and is
  **never re-measured**. After a later build it says `measured on build N`. It has no `expected` and no verdict.
- **Offsets and spans carry no review intent**: `markIntent` is `null` for both, the reviews' intent bar does not apply
  to Measure and Should be here, and neither joins a round. An offset is never exact and never checked against a
  build: `anchorState` stays `ok`.
- **A tracing is cut unspread**, in the object frame of its layout. `Part.arranged` is not applied, and the panel says
  so of a layout shown spread.
- Coordinates crossing a process boundary are in the object frame of the tracing's layout (mm, Z up). A tracing's own
  `[u, v]` are named `uv`, and the frame that maps them is stored with the tracing.
- **Images for Claude are at most 2000 px on the long edge** (default 1280, `checkedImage`). A kept photo may be up to
  4000 px (`checkedPhoto`) because it is the person's, not Claude's. What Claude sees of it is the `tracings`
  `picture: true` picture, and only that picture.
- A tracing never changes the model, and nothing on it does. Claude never lines up, swaps, fades or removes a photo,
  and never changes or removes a tracing or a layer of the person's (it may add layers to one).
- Never write inside the workspace except under `<object>/.torno/`, through `ownTorno` and `writeOwn`. Tracings add no
  write exception to `workspace-writes`. A saved export goes through `askWhere` and `writeExport`. The kernel never
  writes a file. Kernel stdout carries frames only.
- Numbers shown go through `shared/format.ts`. Numbers stored and returned as data are in full. UI text is in sentence
  case, and numbers and refs are set in the monospace face. There is no control-room look, and colours come from
  `styles/tokens.css`. **No per-frame state in React**: pan, zoom, drag and the pointer readout move by refs and
  transforms.
- **Tests never open a visible window** (`show: false` under `TORNO_TEST=1`, no `page.screenshot()`, no clipboard) **and
  never run the real `claude`** (`TORNO_AGENT_CMD` is the stand-in, `node app/test/fake-agent.mjs`).
- **Commits end with `Co-Authored-By: Claude <noreply@anthropic.com>`**, as this repo's `CLAUDE.md` asks.
- Before changing a file, read the `.claude/rules/` files whose `paths:` cover it: `section`, `export-page`,
  `export-saving`, `board`, `marks-store`, `marks-window`, `mcp-tools`, `mcp-read-tools`, `agent-prompt`, `keys`,
  `kernel-measures`, `kernel-supervisor`, `workspace-writes`, `first-screen`, `styles-themes`, `chat-cards-and-refs`,
  `left-column`, `drawing-on-view`. A change to what torno does changes `docs/manual.md` and the rule that says it in
  the same commit.

## Review Focus

1. **A face tracing after a build moves its face.** The plane moves along its normal and its `x` and `y` stay put, so
   the photo, the layers and every `uv` stay. Every mark on that tracing is moved by the same vector in one
   `MarkStore` change and is still in the plane within 1e-6 mm. A face that is gone, or is no longer parallel, leaves
   the plane where it was and says `block/F31 is not in this plane any more`, to the window and to Claude (Tasks 3
   and 11).
2. **Exactness of what a photo touches.** A span with one end on the photo, or not snapped, is `≈`, says how, and keeps
   its value after a rebuild. A span with both ends snapped is `exact on build N`. A line-up point snapped to a kernel
   point is replaced by the kernel's, and one more than 0.01 mm off is refused. The photo's scale, angle and fit say
   `not exact` in the panel, in `tracings`, in the board text and in the export's title block. An offset is never
   exact (Tasks 9, 10 and 12).
3. **The photo sweep deletes only what torno dropped.** Swap and Remove photo list the old file and its straightened
   copy in `dropped.json`. A `tracings.json` from another branch, which names other photos, deletes nothing. A tracing
   removed and then restored in this run keeps its photo through the sweep. A file younger than a minute, a link, and
   an unlisted file are left alone (Task 9).
4. **Ids and ownership survive a pull and every door.** `T3` removed is not given again, even after a pulled file says
   `next: 1`. A window change carrying `id`, `by`, `transform` or `file` has those ignored. `add_layer` on the person's
   tracing makes a layer of Claude's, and `add_layer` naming the person's layer, or `add_tracing` removing the
   person's tracing, is refused by its owner's name with the file untouched (Tasks 2 and 7).
5. **Claude's picture of a 4000 px photo.** It is drawn at 1280 px (or `size`, at most 2000), passes `checkedImage`,
   and is the only way the photo reaches Claude: not the board line, not the prompt, not `tracings` without
   `picture: true`. The export embeds the photo only when "The photo" is ticked, and holds no path of this machine
   (Tasks 4, 7 and 10).

### Task 1: The kernel's `section` takes axes and gives snap points

**Files:**
- Modify: `kernel/src/torno_kernel/section.py` (`section`, `_Frame`, `_cut`, `_outline`)
- Modify: `app/src/shared/geometry.ts` (`Sectioned`, `SectionLoop`)

**Interfaces (produces):**
- `section` args gain optional `axes: { x: [3], y: [3] }`. It must be orthonormal within 1e-6 with `x × y` along the
  normal, else `bad_request`. With axes, `_Frame` uses them in place of its own `x` and `y`, so every `[u, v]` is in
  the tracing's frame. Without them the reply is unchanged.
- `section` args gain optional `snaps: true`. Each loop then also carries:
  - `corners: [u, v][]`: the ends of each cut edge, from the B-rep intersection, not the polyline
  - `circles: Array<{ centre: [u, v]; radius: number; edge?: string }>`: each cut edge that is a circle. `edge` is
    `E<i>` (as `topo` numbers edges) when the arc lies on a circular model edge in the plane.
  - All of these are exact. The `section` MCP tool never asks for snaps, and its answer is unchanged.
- `SectionLoop` gains `corners?` and `circles?` of the same shape. `Sectioned` is unchanged otherwise.
